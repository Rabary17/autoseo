🏗️ Architecture headless

Séparation complète entre le CMS WordPress (données) et le frontend Next.js (présentation). Déploiement sur Vercel avec revalidation ISR automatique.

Flux de données

1️⃣ Rédacteur publie un article

  • Article rédigé dans WordPress (Gutenberg obligatoire)
  • Métadonnées : catégorie = cocon, tags = entités, image à la une native
  • Clic « Publier » dans wp-admin

2️⃣ Webhook WordPress déclenché

  • Hook WordPress publish_post exécute le mu-plugin
  • Envoi POST à https://monauto-tau.vercel.app/api/revalidate avec le slug de l'article
  • Authentification : Authorization: Bearer NEXT_REVALIDATE_SECRET

3️⃣ ISR revalide la page Next.js

  • Endpoint /api/revalidate (Next.js natif) appelle revalidatePath(path)
  • La page de l'article est retirée du cache ISR
  • Catégorie parente aussi revalidée (la liste des articles mise à jour)
  • Réponse immédiate au webhook

4️⃣ Visiteur accède à la page

  • Si page en cache ISR : servie en <100ms (statique)
  • Si cache expiré ou revalidée : requête à l'API WordPress, génération, re-cache (ISR)
  • Durée de cache : 900s (15 min) — filet de sécurité

Points clés

Avantages de cette archi

  • Pas de coupling : WordPress peut être remplacé, migré, mis en maintenance sans impact frontend
  • Performance : Pages statiques/cachées = temps de réponse <100ms (vs WordPress ~300-500ms)
  • Scalabilité : Vercel gère les pics sans infrastructure coûteuse
  • SEO natif : Next.js génère sitemap.xml, robots.txt, JSON-LD automatiques
  • Déploiement simplifié : Frontend sur Vercel (git-based), WordPress sur n'importe quel hébergement

Challenges résolus

  • Images : WordPress Imagify (compression/WebP à l'upload) plutôt que next/image (trop coûteux à 10k articles)
  • Polices : Stack système (pas Google Fonts — réseau indisponible ici)
  • Revalidation : Webhook au lieu de rebuild quotidien (économie 10x)
  • ACF : Free tier utilisé (pas de Repeater — structuration simple : texte sur 1 ligne par entrée)
